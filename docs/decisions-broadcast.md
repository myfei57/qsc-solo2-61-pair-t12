# 应急广播分区播放与抢占 — 设计决策记录

## 决策 1：高优先级打断方式 —— 立即硬切（`preempt_mode = immediate`）

火警（优先级 90）到达时，**立即切掉**目标分区当前正在播的内容，先插入约 1 秒
提示音（`ATTENTION_TONE_SECONDS`）再播报警示；不等当前一句话播完。

- 理由：管廊疏散场景中可懂度要让位于时效。等句子边界可能让疏散指令延迟数秒到
  十几秒，且等待时长随当前内容不可控；硬切 + 提示音能给出明确的声源变化，现场
  人员对“换内容”反而更敏感。
- 代价：被打断的句子不完整。系统将被抢占的广播**原样重新入队**（标记
  `preempted`，排序在普通排队之前），火警播完后自动续播，不丢内容。
- 实现位置：`tunnelnet/broadcast/model.py` 常量、`service.py::_start_zone`。

被否决方案：`sentence_boundary`（等一句播完）。对循环播报（火警本身往往循环）
没有明确的“一句话”边界，且低优先级内容可借此长期占用扬声器。

## 决策 2：播控失败退回范围 —— 按分区退回（`fallback_scope = zone`）

部分分区播控失败时，**只有失败的分区**退回就地疏散指示（指示灯/本地指示牌），
健康分区保留语音；不整区退回。

- 理由：播控放大器按分区独立部署，A 分区功放故障不代表 B 分区没有语音能力。整
  区退回会主动放弃仍健康的语音通道，减少有效信息覆盖。
- 但命令作为整体必须有事务性：已经成功开播的健康分区要执行 **Saga 补偿回滚**
  （停掉刚切过去的火警、恢复被它抢占的原广播或回到空闲），使失败命令不留半截
  状态；失败分区只亮就地指示。
- 准备阶段就已离线（ping 不通）的分区从未开始，不触发对其他健康分区的回滚，
  只本分区亮指示。
- 实现位置：`service.py::trigger` 的 prepare / commit / compensate 三段。

被否决方案：`all`（任一分区分败则整批退回指示）。牺牲健康分区语音，不符合设备
独立失效的现场实际。

## 其他固定语义

- **单一事实来源**：分区表、播控队列、命令台账、控制台投影、审计流水全部是对
  同一条事件序列（`broadcast/store.py::EventStore`）的折叠（`state.py::fold`）。
  控制台读到的就是现场执行的同一份状态，不存在两份对账数据；事件流通过 sink
  镜像进总审计（`runtime.py`）。
- **时序依赖 / 屏障**：每次接管推进该分区单调递增的 `epoch`；定时器完成回调、
  迟到的硬件失败回报都携带 epoch，过期回调一律丢弃，抢不到新广播。回滚同样推进
  epoch，使失败命令的一切在途回调失效。
- **幂等**：同一 `key`（或显式 `idempotency_key`）在命令存活期（accepted/
  playing/queued/partial/rolled_back）内重复触发，返回原 `command_id` 与相同结果，
  只追加一条 `command_duplicate` 审计；命令结束后同 key 可再次触发。
- **优先级排队**：每分区独立队列，按优先级降序，抢占恢复项优先于普通提交，同级
  FIFO。优先级常量：routine 10 < notice 30 < abnormal 60 < fire 90，也可用 1–100
  整数。
- **播控故障可被发现**：`HeartbeatMonitor` 周期性 ping 每个分区功放，丢失即标记
  离线、停在播、亮就地指示；恢复后撤销指示并续播队列。
